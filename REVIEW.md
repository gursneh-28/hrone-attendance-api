# REVIEW.md

Defects found in the starter `app/main.py` (helpers and endpoints). I confirmed each one with a failing request or call before fixing it, and re-ran the same checks afterwards.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | The 10-minute grace check is done on already-floored minutes, so a punch-in a few seconds past the grace period counts as on time. R2 says late only if strictly more than 600 s after shift start. | Shift 09:30, punch-in 09:40:01: returns 0, R2 says 10. (09:40:00 -> 0 and 10:15:59 -> 45 are already right, so the bug hides on the boundary.) | Compute whole seconds since shift start, test `> 600`, then return `seconds // 60`. |
| 2 | `compute_late_minutes`, `punch_in`, `compute_overtime` | Overnight shifts (`shift_end <= shift_start`) are ignored. The date is the plain punch-in date, the shift start is placed on the punch-in's own day, and the shift end is placed on the attendance day instead of the next day (R1). | Shift 22:00-06:00, punch-in 7 Jul 02:00: date comes out 7 Jul (should be 6 Jul) and late 0 (should be 240). Overtime for an out at 7 Jul 06:40 comes out 1480 min instead of 40. | New `attendance_date` (punch-in earlier than `shift_end` belongs to the previous day) and `shift_window` (end falls on the next day for overnight shifts). Late and overtime now take the shift start/end instants from it. |
| 3 | `punch_in`, `create_employee`, `MongoClient` | Time zones. `datetime.fromtimestamp(ms/1000)` and `datetime.now()` produce naive datetimes in the server's local zone. Mongo treats naive values as UTC, so on an IST machine every stored instant is 5.5 hours off. The client also returned naive datetimes on read. | Punch-in at 3 Aug 09:40:01 IST should be stored as 04:10:01 UTC; the starter stored 09:40:01 UTC. | One convention: inside the app every instant is an aware UTC datetime. `from_ms`/`to_ms` convert only at the API boundary. Client created with `tz_aware=True`. IST is used only to get a calendar date or place a shift time. |
| 4 | all helpers, `punch_in` | Instants are not truncated to whole seconds (R1), so 09:40:00.900 would be stored and used in calculations as is. | Send `punched_at` with 900 ms: the stored and returned value keeps the milliseconds. | `from_ms` and `now_utc` truncate to whole seconds; the truncated value is what is stored and returned. |
| 5 | `compute_work_hours` | Uses Python `round()`, which is not half-up (it rounds binary floats, and ties go to even). R4 requires half-up. | 9630 s = 2.675 h: returns 2.67, R4 says 2.68. | Compute with `Decimal(seconds) / Decimal(3600)` and `quantize(Decimal("0.01"), ROUND_HALF_UP)`. |
| 6 | `compute_overtime` | No 30-minute minimum (R3): any positive gap counts. It also crashes (naive vs aware datetime) if given a punch-out read from Mongo with default settings. | Shift end 18:30, punch-out 18:45: returns 15, R3 says 0. | Floor to whole minutes and return the value only if `>= 30`, else 0. All datetimes are aware UTC now, so no naive/aware mixing. |
| 7 | `EmployeeIn`, `PunchInIn` | No input validation. Any string passes for emp_code, email, shift times and joined_on; `shift_start == shift_end` is accepted; `status` accepts anything (ABSENT, LEAVE, garbage); `punched_at` accepts seconds, floats and out-of-range numbers; a `punched_at` of 0 is treated as missing. | POST /employees with email `not-an-email`, shift_start == shift_end, joined_on `yesterday`: 201 instead of 422. Punch-in with `punched_at: 1783312500` (seconds) creates a record in January 1970. Punch-in with status ABSENT: 201. | Pydantic patterns and length limits from the contract, a model validator for shift times and a real calendar date, `status` limited to PRESENT/WFH/ON_DUTY, and a strict integer type for `punched_at` limited to the epoch-millisecond range. |
| 8 | `list_employees` | Four bugs: `skip = page * page_size` skips the first page; `total` counts the whole collection, not the filtered set; no sort by `emp_code`; no bounds on `page` / `page_size` (R10). | `?page=1&page_size=2` returns EMP0003 and EMP0004 instead of EMP0001 and EMP0002. `?department=Engineering` returns total 9 instead of 2. `page_size=1000` and `page=0` return 200. | `skip = (page - 1) * page_size`, `count_documents` on the same filter, `.sort("emp_code")`, and `Query(ge=1)` / `Query(ge=1, le=100)`. |
| 9 | `punch_in` | Unknown employee: `emp` is `None`, so `emp["shift_start"]` raises `TypeError` and the client gets a 500. | POST /attendance/punch-in with `emp_code` EMP00000: 500 (traceback in the server log). | Explicit `if emp is None: raise HTTPException(404)`. |
| 10 | `create_employee`, `punch_in` | Check-then-insert races. Two requests can both pass the `find_one` check before either inserts. | 8 simultaneous punch-ins for the same employee and date: three returned 201, the contract needs exactly one. (The employee-create race can pass by luck, but has the same flaw.) | Unique indexes (`emp_code` on employees, `(emp_code, date)` on attendance_logs), insert directly, and turn `DuplicateKeyError` into 409. The database decides, not the code. |
| 11 | `create_employee`, `punch_in`, `list_attendance` | Response shape does not match the contract: `_id`-derived `id` is returned, instants are datetimes (ISO strings) instead of epoch milliseconds, and legacy records without `half_day` or `history` are returned as they are, with those fields missing. | Response key list contains `id`; `punch_in` is `"2026-08-03T09:40:01"`; the legacy EMP0002 record comes back without `half_day` and `history`. | `serialize_employee` and `serialize_attendance` build the response explicitly: no `id`, `to_ms` for instants (including inside `history`), and defaults of 0 / false / `[]` for missing fields. |
| 12 | `list_attendance` | Loads the whole collection into memory, sorts in Python, slices in Python and counts with `len()`: slow and memory-hungry at 100k records. Sorts by `date` only (contract: date descending, then `emp_code` ascending). No validation of dates, status or page bounds. | `date_from=2026-07-10&date_to=2026-07-01` returns 200 (should be 422). `status=FOO` returns 200. `page_size=1000` returns 200. The slowdown only shows up at scale. | Database-side `.sort([("date", -1), ("emp_code", 1)])`, `.skip().limit()` and `count_documents`. Real-date check on `date_from` / `date_to`, 422 when `date_from > date_to`, a `Status` enum, and page bounds. |
| 13 | startup (missing) | No indexes are created, so every list or lookup is a collection scan, and the uniqueness guarantees from row 10 do not exist. | `list_indexes()` shows only `_id_` on both collections. | `ensure_indexes()` runs in the FastAPI lifespan at startup and is idempotent. Employees: unique `emp_code`, and `(department, emp_code)`. Attendance: unique `(emp_code, date)`, `(date desc, emp_code)`, and `(status, date desc, emp_code)`. |
| 14 | `health` | Always returns `{"status": "ok"}`, even when MongoDB is down. The contract needs 503 in that case. | `docker stop hrone-mongo`, then GET /health: still 200. | `client.admin.command("ping")`; on `PyMongoError` raise 503. The client uses a 5 s `serverSelectionTimeoutMS` so the probe answers quickly instead of hanging. |

## Looked at and decided it was not a defect

- `load_dotenv()` is called with the default `override=False`, so real environment variables still win over `.env`, as the contract requires.
- The 201 status codes on POST /employees and POST /attendance/punch-in are correct.
- Filtering `date` with `$gte` / `$lte` on strings works, because `YYYY-MM-DD` sorts the same way as the calendar. This only holds if the format is validated, which is part of row 12.
- The `IST` constant (UTC+05:30) is defined correctly. The bug was in how it was (not) used.
- The starter never returns `_id` from `/employees`, so that endpoint was not leaking it. (`/attendance` and punch-in did leak an `id`, see row 11.)

## Known limits I did not change

- `skip` / `limit` pagination gets slower on very deep pages of a huge collection; I would switch to keyset pagination for 100x data (see DECISIONS.md).
- Creating the unique indexes fails at startup if the existing data already contains duplicates. The contract says the data is unique, so I treat that as a data error rather than handling it.
